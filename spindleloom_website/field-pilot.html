FLEET-EVAL.md proves the fleet coordinates on a fixed brief in a scratch directory. It cannot show what happens when the same fleet meets a codebase with history: stale documents, a work-item tracker that disagrees with the code, two initiatives sharing one repository, and a team that will not stop shipping while you audit them. This record is that second question, answered over eight runs. It is written for two readers: an adopter deciding whether the discipline survives contact with a real repo, and a maintainer deciding what to build next.

Read the honesty note first. There is no baseline, no control team, and no independent judge. Every run was driven by an AI session operating the fleet, and that same session wrote the findings. What this record can honestly show is what broke, what caught it, and what was still missing - not a productivity number. Where a claim rests only on the operator's own say-so, it says so.

The host application

De-identified. Structure preserved, identity removed - no client, product, module, ticket, branch, or person name appears anywhere in this record, and quantities are given as bands rather than exact counts.

DimensionWhat it was
DomainRegulated-industry operations: high-volume document ingestion, rule-based evaluation against a regulatory ruleset, human-in-the-loop review of machine judgments, and an immutable audit trail over every decision
StackPython service backend, React/TypeScript frontend, managed container hosting (replicated in production), a managed NoSQL store, an enterprise work-item tracker as the delivery system of record
TeamA mid-size pod - sponsor, PM (wearing the PO hat), architect, leads, developers, QA. Team composition is context from the engagement, not something these runs measured.
RepositoryOne repo, two parallel initiatives, a governed docs tree in the low hundreds of files carrying a comparable number of requirement IDs across ADRs, backlogs, RTMs, sprint plans and threat models
Verticals touchedA compliance module (the primary subject), a public-filings module, a legal module, a net-new life-sciences vertical, and a cross-cutting knowledge layer spanning all four

Why it was a fair test: the repo was not scaffolded by this toolkit. It arrived with its own ADR numbering, its own document tree, its own conventions, and a second initiative the Standard has no vocabulary for. Every conformance finding below is a real adoption cost, not a self-inflicted one.

Method

Two distinct modes ran, and the difference matters when reading the findings:

  1. Runs 1-4 - the toolkit reasons, the host's own agents execute. The fleet's discipline

    2. (gates, traceability, contract-shaped handoffs) was applied by an operator using the host repo's own agent definitions. These runs test the method.

  2. Runs 5-8 - the installed plugin drives and executes. The distributed fleet

    3. (sloom:* subagents plus its MCP tools) ran recon -> design -> ADR -> backlog -> estimation -> build -> three review gates -> fix -> re-verify, producing merge-ready code on a local branch. No pull request was opened during the pilot; "shipped" below means reviewed and landed locally, never deployed.

Fidelity caveats, stated because the runs were not uniform. Runs 5, 6 and 8 declared a 16-dispatch budget up front and recorded every step in a run ledger; runs 5 and 6 landed exactly on budget, and run 8 went two over, both spent closing execution-confirmed defects and recorded before the overrun rather than after. Run 7 did neither: it kept no run ledger (dispatches were tracked in the operating session's own task list), declared no budget, and ran its three review gates with the host repo's reviewer agents rather than the fleet's - so it is a weaker data point for the product than runs 5, 6 and 8, and is reported that way below.

What held up

Recorded deliberately, because a gap catalog alone reads as a failure log:

  • Adversarial verification is real. Across four build runs, checkers rebuilt acceptance

    • matrices from source rather than trusting summaries, re-diffed a deliberately duplicated code path line-by-line for security divergence, and twice proved a test's discriminating power by breaking the code under it. In run 8 they went further and treated the maker's own mutation-proof as a claim requiring independent re-verification.

  • Checkers found new defects, not just confirmation. The highest-value review findings

    • were things nobody had asked about: an accessibility defect behind green tests, an error-envelope inconsistency three times worse than believed, and a latent crash class present in two already-shipped components.

  • Agents audited the operator. A backlog agent overturned the operating session's own

    • prior status claims - twice, with evidence. Independent verification worked on the person running the pilot, which is the sharpest available test of the builder-is-not-verifier rule.

  • Recon before design paid for itself repeatedly. Four runs had their own plan corrected

    • before code: two fatal linker defects caught at planning time, a wrong extension point, a wrong service to mirror, and a proposed abstraction that duplicated an existing one.

  • Refusal was used correctly. Agents declined to force a story to Ready over a real unowned

    • dependency, declined to invent a filename that did not exist yet, declined a false-precision estimate, and declined to force-reuse a component that did not fit - each time stating why.

  • Registers were extended, not duplicated. Both keeper agents checked for a pre-existing

    • register before creating one, and verified the claims they were handed with fresh searches rather than transcribing them.

  • The loop shape survived losing its tooling. With the CLI absent (gap 16), a hand-rolled

    • propose -> confirm -> dispatch loop still kept the human at the right altitude: architecture calls and scope changes got an explicit decision, routine dispatches did not.

  • Context handoff worked when it was used. Run 2 persisted a synthesized finding register

    • for downstream agents - the one positive data point for the mechanism gap 20 criticizes.

The gap catalog

Twenty-one numbered gaps, generalized. Gap 10 was retracted by its own author. Gaps 11 and 12 were catalogued in the host repo's evolution log rather than here, to avoid the exact "same claim in two places" drift the pilot kept finding; they are summarized but not re-derived.

Status is against the current release of this toolkit, verified by reading the code - not by assuming the name of a feature implies its behavior. One gap is closed (16, fixed in response to this record); ten are partially addressed, seven remain open, and two were never re-assessed.

Two frictions that never got a number

Recorded because both had real consequences and neither fits the numbered catalog:

  • No "gated / conditional" state on a planned work item. A story whose own recon had

    • declared it blocked was still committed into a sprint at 8 points, because "don't commit until cleared" existed only as prose with nothing enforcing it.

  • Parallel review gates can finalize on stale peer state. With three reviewers dispatched

    • at once, one filed "no evidence of a security sign-off" as a blocking finding while that sign-off was landing in the same batch. It self-corrected within the turn, and parallelizing the gates is still right, but a shared "gates landed so far" view would remove the friction.

What the shape of this catalog says

The pilot's own conclusion, and an independent code review agrees: the agents are the strongest part of the system and the scaffolding around them is the weakest. Not one gap in Group C is about an agent's judgment. They are all about the plumbing an orchestrator needs and does not have - a shipped CLI, a run registry, a dispatch counter, a way for a specialist to persist what it learned. Group A says the same thing at the other end of the pipeline: the blind spots cluster before recon and after review, not in the middle where the reasoning happens.

What to build next

The pilot's own prescriptions, carried forward verbatim in intent. These are registered in IMPROVEMENTS.md:

  1. ~~Ship the referenced tooling, or branch the docs.~~ Done - the generator computes

    2. the CLI's import closure and every bundle ships it; validate_targets and a standalone smoke test hold it there (gap 16, IMP-160).

  2. Derive the run ledger's readable half from its machine half, or add a save-run-state

    3. tool mirroring the context-save shape (gap 17).

  3. Add a dispatch/spend read so budget enforcement stops being unaided arithmetic (gap 18).
  4. Add a reserve-next-id call so parallel writers can cross-reference correctly on first

    5. write (gap 19).

  5. **Expose the context tools to specialists, or state plainly that persistence is the

    6. orchestrator's job** - the skill currently implies the opposite (gap 20).

  6. Add a doc-ownership lease or a queryable run registry so a starting run can discover an

    7. active one before writing shared state (gap 21).

  7. Require an intake stub (source, date, author, one-line premise) as the first write for

    8. any externally-authored artifact, before recon spend (gap 13).

  8. Force a prior-art position (reuse / extend / justify-new) whenever a proposal introduces

    9. a config-object, manifest, or profile abstraction (gap 14).

  9. Add a scope field to the backlog row - net-new-vertical / extend-vertical / cross-cutting
  • so estimation can apply different scrutiny to each (gap 15).

What an adopter should take from this

Seven practices earned their place under real pressure. None of them require a toolkit change:

  1. Verify by execution, never by reading. A test that exists is not a criterion that is

    2. met. Where it matters, break the code deliberately and watch the test fail before you trust it.

  2. Treat the maker's own proof as a claim. The strongest runs had the checker independently

    3. reproduce the mutation, not read about it.

  3. Read past the green tests. Two of the pilot's best findings were defects that every test

    4. passed over: a test suite that captured logs and asserted nothing, and a component whose own accessibility claim its tests never checked.

  4. Recon before design, always - including recon of your own plan. Four runs had a written

    5. plan corrected before code, each time by reading the actual source rather than the document.

  5. Fan out with genuinely different lenses, then keep the disagreements. Where two lenses

    6. contradicted each other, the contradiction was the finding.

  6. Re-read a shared document immediately before editing it. With no locking, this was the

    7. only defense that worked - and it is not sufficient: two sessions still minted the same ID independently, because re-reading protects text, not identifiers.

  7. Record a budget overrun before you spend it, and only for an execution-confirmed defect.

    8. Transparent overrun beat both rigid enforcement and silent drift.

And one for maintainers of any agent fleet: ship the tooling your agent definitions assume, or make the definitions branch. Gap 16 forced hand-rolled workarounds in three of the four product runs.

Limitations

  • No baseline, no control, no independent judge. Nothing here supports a claim about speed,

    • cost, or defect rate. The productivity question needs the human-team pilot in archive/PILOT-PLAN.md, which remains unrun.

  • The operator wrote the findings. Mitigated in places (agents overturned the operator's own

    • claims twice) but not eliminated.

  • One codebase, one domain, one team. Regulated-industry document processing is a favorable

    • case for a traceability-heavy toolkit; a fast-moving consumer product might report differently.

  • Runs 1-4 tested the method, not the product. Only runs 5-8 exercised the distributed fleet

    • as an adopter would receive it - and run 7 did so at reduced fidelity (see Method).

  • Nothing was released. The runs produced merge-ready code on a local branch; no pull

    • request, no deployment, no production observation.

  • The statuses above are a code read, not a re-run. They say what the current release

    • implements, not that a ninth run would find the gap gone.
